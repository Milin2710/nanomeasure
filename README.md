# NanoMeasure — TEM Image-Based Nanoparticle Diameter Regression

Predicts a nanoparticle's physical diameter (nm) from a TEM-style image, as a
**regression** problem rather than classification: classical feature-based
baseline → CNN transfer-learning regressor → ablation study → MC-Dropout
uncertainty → Grad-CAM interpretability → interactive demo app.

## A scientific note on the dataset — read this first

**The dataset used here is synthetic, generated by `data/generate_dataset.py`,
not a downloaded real-world TEM dataset.** This needs to be stated plainly:

- An external public dataset (a Dryad HRTEM nanoparticle set) was the first
  choice, but this environment does not have reliable outbound access to
  arbitrary external repositories, so it could not be downloaded here.
- Rather than fabricate results or skip straight to a toy demo, the project
  generates a **procedural synthetic benchmark with known ground truth**
  (1,500 images: 1,000 train / 250 val / 250 test), and every number reported
  below is a real measurement against that benchmark — nothing here is
  invented. See `data/generate_dataset.py` for exactly how each image is
  built (blob-shaped particle, mass-thickness contrast, support-film texture,
  edge blur, Poisson shot noise, randomized per-image pixel scale).
- This is a real limitation, not a cosmetic one: a model that performs well
  on this synthetic set is not thereby validated on real experimental TEM
  images, the same way VibeTube's own simulated benchmark is a first-pass
  validation, not a replacement for its experimental HRTEM comparison. The
  honest framing is **"pipeline validated on a controlled synthetic
  benchmark; not yet tested on real experimental images."**
- The code is structured so a real dataset can be substituted directly: drop
  real images + a `metadata.json` of the same shape (`filename`,
  `diameter_nm`, `pixel_scale_nm_per_px`, `split`) into `data/`, and every
  downstream script (features, training, ablation, app) works unchanged.

## The core scientific issue this project addresses

Diameter is a physical quantity, but a model trained on raw pixels alone
can't tell the difference between "a 10 nm particle imaged at high
magnification" and "a 20 nm particle imaged at half that magnification" —
both can occupy the same number of pixels. Pixel size (nm/pixel) varies
per-image here, deliberately, to force this issue. Two fixes are compared:

1. **Classical baseline**: pixel-based shape features (equivalent diameter
   in pixels, etc.) are explicitly multiplied by the image's pixel scale
   before being handed to the regressor — the scale is a feature, not
   something the model has to discover.
2. **CNN**: an ablation (`ablA_*` in Experiment 3) compares a model with no
   scale information, against one where the scale value is appended as a
   4th input channel — directly testing whether giving the network explicit
   scale information helps.

## Running it

```bash
pip install -r requirements.txt

# 1. Generate the synthetic dataset (fast, ~30s)
python data/generate_dataset.py

# 2. Classical baseline
python src/baseline_classical.py

# 3. Main CNN model (normalized input + scale channel + full fine-tune)
python src/train_cnn.py --name main --normalize --scale-channel --backbone finetune --epochs 10

# 4. Ablation study (6 training runs; ~15-25 min on CPU)
python src/ablation.py

# 5. Interactive demo (needs step 3 done first)
streamlit run app/streamlit_app.py
```

## Results

See **[`RESULTS_SUMMARY.md`](RESULTS_SUMMARY.md)** for the full write-up —
every number in it comes from an actual run of this code (`results/*.json`,
`results/plots/`). Headline findings:

| | MAE (nm) | R² |
|---|---|---|
| Classical baseline (Random Forest) | 3.11 | 0.46 |
| CNN (ResNet18, random init, scale-aware) | 3.41 | 0.43 |

- The CNN does **not** clearly beat the classical baseline here — see
  `RESULTS_SUMMARY.md` for why (no pretrained weights available in this
  sandbox; see "What I would NOT claim" below).
- **A real bug was found and root-caused, not hidden:** the synthetic
  generator's radius clipping (added to keep particles in-frame) silently
  caps rendered particle size for 76.6% of images, and 98.1% of images with
  true diameter > 8 nm — meaning most large-diameter images don't actually
  encode their true diameter. This, not model quality, is the dominant
  limit on every R² above. Full detail and a proposed fix in
  `RESULTS_SUMMARY.md`.
- MC-Dropout uncertainty correlates with actual error (r ≈ 0.49) on a
  20-image spot check — noisy but directionally useful.
- Grad-CAM shows the model partly attending to image borders/background,
  not purely the particle — flagged as a real limitation, not polished away.

## What I would NOT claim

- That this reproduces or validates VibeTube, or any experimental TEM result.
- That synthetic-benchmark accuracy predicts real-world accuracy.
- That this is a from-scratch physics simulator — `generate_dataset.py` is a
  fast procedural renderer, explicitly **not** a multislice/CTF simulation
  the way abTEM (used by VibeTube) is.
